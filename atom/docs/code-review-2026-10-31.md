# 2026-10-31 核心代码审阅与修复

本轮采用的原则：先找用户可见的失败，再修数据和生命周期边界；保留已工作接口、用户数据和协作中的改动。没有对上游移植源码作整仓格式化或框架重写。

**交付范围：本地源码与隔离测试。尚未发布到 GitHub、云服务、Mac 安装包或灰色设备。** 工作区已有相册、钢琴、语音、导航等未提交改动，本轮是在这些改动上验证，不能把结果当成线上版本的证明。

## 已修复的实际问题

| 优先级 | 问题与影响 | 修复与验证 |
| --- | --- | --- |
| P1 | 市场初始化导入官方包时仍限 1 MiB，带采样的钢琴包约 1.28 MB，导致整个市场初始化失败，并连带阻断中继启动。设备市场入口也限 1 MiB；Mac Studio 又误用 96 KiB 的普通 Agent 产物限制。 | 市场和 Studio 源码预算改为 1984 KiB，HTTP 请求仍限 2 MiB，预留元数据空间；设备市场交付检查使用现有 2 MiB 上限。普通 Agent 任务产物保留 96 KiB。新增真实钢琴包的市场读写、Mac 源码保存、设备 HTTP 预览/安装/更新测试，核对采样资源和安装时间保留。 |
| P1 | `Experiences.cancel()` 只改变任务状态，但原网络请求仍运行。以任务状态计算并发名额，连续取消再创建就能突破两个后台请求上限。 | 独立记录真正存活的 worker；线程退出才归还名额；历史清理不得删除仍被 worker 使用的任务。两个阻塞请求取消后连续 70 次新建均被拒绝，原请求完成后释放名额，迟到结果不发布。取消不表示上游停止计费。 |
| P2 | 创作或工作坊线程启动失败后，任务可能永远显示排队并占用容量。 | 两个入口均将启动失败转换为明确失败状态；创作同时释放预留名额。注入线程启动异常验证可继续创建。 |
| P1 | Mac Studio 替换源码时先删除当前目录，再重命名新目录；替换失败会使工作区源码消失。缓存还会提前改成未落盘的版本。 | 先完整写入临时目录，交换前保留旧目录，失败回滚；交换中途进程退出后，下次访问恢复旧目录；完整写入成功后才更新源码缓存。保留一份 `source-previous/`。注入 rename 和源码写入失败，确认旧文件、草稿内容与版本不变。 |
| P2 | Mac 私有 JSON 的原子重命名前未显式 fsync，写入异常还可能遗留临时文件。 | 先序列化、写入并 fsync，关闭后原子替换；Unix 同步父目录；失败清理临时文件。注入文件 flush 和 rename 异常，原文件保留；成功文件权限为 0600。 |
| P2 | 桌面新增的排序模式和使用频次未加入用户数据白名单，备份/恢复或镜像会遗漏。 | 前后端一起纳入 `atom.desktop.sort.v1`、`atom.desktop.usage.v1`；验证后端备份恢复和浏览器空存储恢复。 |

另修正 Mac 源码校验允许 `files.manifest.json` 与独立 manifest 冲突的问题。该路径现在明确拒绝，与市场和设备安装契约一致。

## 审阅判断

- **三端职责继续保留。** 设备承担界面和硬件交互；电脑伴侣承接本机 Agent 和源码工作区；服务器负责账号、中继、市场与同步。没有证据支持为了“统一技术栈”迁移这些已运行的模块。
- **主要缺陷在跨模块契约。** 包大小、取消状态与真正资源占用、保存内容与落盘确认，分别在多个模块里有不同假设。本轮修正这些边界，并用同一个真实应用包跨端验证。
- **已有恢复机制继续使用。** 系统核心更新已经有持久化 journal、验签与失败回滚；设备存档已经有前一份副本。没有另造一套更新器或数据库层。
- **可读性应随修改逐步改善。** `studio.mjs` 和部分 UI 仍有很长的单行函数；本轮把实际修改的源码工作区方法展开，但没有用纯格式化掩盖行为改动。

## 本轮未作出的保证

1. 未逐个操作全部移植应用，未把浏览器 fixtures 当成灰板 GPU、录音或帧率验收。
2. 文件 fsync、异常回滚和进程中断不等于真实突然断电验收；Studio 元数据与源码目录也不是一个跨文件事务。设备应用目录更新的进程退出测试已在下方第二轮补充，物理断电仍未验收。
3. 市场仍把官方应用的主许可证显示为 MIT；钢琴的 `SOURCE.md` 已区分代码、采样和乐谱许可，但目录的单字段不能完整表达资源许可。对外发布需保持素材声明，并进一步完善展示；本轮没有擅自改写上游许可证。
4. 旧 BSP 显示专项按用户原决定关闭跟进，本轮不将其标记为根治，也未重启 LightDM。Apple 正式签名、SMTP 和实物外设验收仍以研发基线为准。
5. 真实发布应从明确的协作提交构建，分开记录设备版本、Mac 包和服务器 release。本地测试通过不自动更新这些已部署组件。

## 第二轮：账号隔离、解密失败与应用更新中断

用户确认审阅建议后，已修复另外三项隔离复现的问题，仍仅修改本地源码，未推送或部署。

1. **跨账号同步（P1）**：原同步循环捕获旧队列，却逐条使用当前账号请求；账号切换的 409 被当成记录冲突后继续发送。现在 `private-sync.mjs` 共享便签/日程的同步逻辑，固定账号对象、令牌、密钥和服务器，异步返回与下一次发送前校验。变更直接终止，不清理原队列；只有携带服务器当前记录的真实版本冲突进入冲突处理。列表加载、保存后的反馈和旧明文加密迁移同样检查会话。
2. **解密错误写回（P1）**：原实现删除密文信息并生成 `[无法解密]` 正文。现在解密/明文结构错误明确失败，不更改原记录、不替换最后可读缓存；持久化当前账号对应集合的写入暂停状态，重启不能绕过。完整读取成功才恢复。Mac 界面禁用编辑，提供重试和重新解锁，也不会误报“已同步”。
3. **设备应用更新丢失入口（P2）**：新资源先完整写入并同步，再写 `apps/.app-update.json` 后交换目录。未提交的 journal 表示回退到旧资源；启动、列出应用和下一次安装/卸载前会恢复。路径与备份身份验证失败时保留现场，不猜测删除目录。已提交成功后留下的备份不触发误回退。历史无 journal 的备份不自动处理。

新增测试：

- `connect/computer/test/private-sync.test.mjs`：12 项，覆盖便签/日程同步中切账号、切服务器、退出；延迟列表响应；解密失败及跨重启写保护；恢复后可保存；旧明文迁移中切账号；无法解密的冲突保留本地正文。
- `tests/test_app_update_recovery.py`：4 项，包含独立进程 `os._exit(91)` 在备份前、替换前、替换后退出；恢复幂等、资源完整与安装时间保留；提交后退出不回退；非法日志不改文件；官方受保护客户端可恢复。
- `connect/computer/private-sync-ui.test.cjs`：真实本地 Dashboard/HTTP，假上游；解密错误锁定编辑、提供重试、恢复便签和日程、不发送写请求、不出现全页滚动。
