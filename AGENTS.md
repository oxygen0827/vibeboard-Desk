# ATOM application requirements

Every application created, imported, ported from GitHub, or updated for ATOM must have its own purpose-specific desktop icon. This applies equally to Codex development and the on-device workshop. Do not ship the shared plus-sign placeholder.

Use a bundled static `icon.svg`, a square `viewBox="0 0 64 64"`, and `manifest.icon="icon.svg"`. Design a recognizable transparent, monochrome pictogram related to the actual function. Use currentColor for strokes/intentional solid marks; the active theme owns colors, tile surface, border, corner radius and stroke weight. Never bake a theme palette, background tile, badge or shadow into application icons. Avoid tiny text, external resources, embedded images, scripts, events, links, and active SVG content. Keep icons below 32 KiB. Preserve valid user-designed icons on updates. New apps must include their icon in the source bundle; installer auto-generation is a compatibility fallback, not a substitute for reviewing the icon's design.

Run `python3 atom/tools/prepare_icon_bundles.py` after rebuilding port bundles or templates, and verify icons on the real desktop. `atom/app_icons.py` contains the shared validator and deterministic fallback generator. Use `atom/tools/ensure_app_icons.py` to backfill installed folders without changing installation timestamps or desktop order.

Keep applications fullscreen with no permanent system chrome. Scroll only within necessary content regions. Preserve Home return behavior and homepage wheel pagination. Newly installed apps append to the desktop; updates retain their position. When deploying complete GitHub ports, copy all resources, not just the entry-only JSON bundle. Never expose model credentials in app files, logs, screenshots, or commits.

Theme packages may provide validated `icons` tokens and per-app `overrides`. All built-in and installed icons use the same theme renderer. Workshop theme selection is a design reference; apps follow the current system theme by default. A fixed app theme is an explicit opt-in. Ported app control chrome should opt into `manifest.theme_ui="controls"`; preserve meaningful scene and data colors.

Application lifecycle and persistence: the shell injects AtomApp v1 before app scripts. For async initialization use AtomApp.deferReady()/ready(). Use AtomApp.load(defaultState) and await AtomApp.save(JSON) for device persistence, with a 64 KiB per-app limit; preview storage is temporary. Never assume localStorage in opaque app iframes. Report save success only after acknowledgment; if reading fails offer retry and avoid overwriting existing records with defaults. Release timers, audio and GPU work with AtomApp.onSuspend. Keep task feedback tied to actual states and respect reduced motion. See atom/docs/app-contract.md.

Desktop navigation: exiting an application returns to the desktop page from which it was opened. Pressing Home while already on the desktop returns to the first page. Apply the same return behavior to built-in apps, installed apps, previews and launch-error screens.

Desktop icon management: short click opens an app; hold primary pointer for 600 ms opens the app action sheet. Movement cancels long press so homepage dragging remains reliable. Built-in apps are protected; uninstall requires explicit confirmation and truthful data-retention messaging. Preserve remaining app order and show actionable failure states.

Marketplace presentation: application cards use a reviewed screenshot of the application's home screen as their background. Keep this cover separate from the theme-aware desktop icon and from executable source bundles. After generating or modifying an application, remind users that ATOM Connect → 我的创作 → 首页截图 accepts a cover upload; the publishing dialog requires a cover in the current client. Use actual rendered UI, never fabricated screenshots. Use empty or clearly identified demo data when capturing private-data applications. Draft covers remain private until publication; replacements must preserve the previous cover on failure. See atom/docs/market-covers.md.

Five-way input is mandatory for every new/updated/published ATOM application. Read and follow atom/docs/input-standard.md (authoritative v1). Declare manifest.input with integer version=1, profile="five-way", back="root" or "custom"; nested pages register AtomApp.navigation.setBackHandler. Canvas scenes explicitly declare scene="controls" with semantic DOM actions, or "passive" for viewing-only artwork. Do not auto-add declarations to unadapted apps. Reserve the top-left 48×48 area for the back control. Do not globally intercept Space/arrows; long Space is system voice/dictation. Run atom/tools/check_app.py and actual five-way flow checks. Static admission does not certify dynamic operation. Existing installed apps and legacy seed migration remain compatibility-only until individually adapted.

Focus animation is owned by the injected input runtime, including movement, sizing and confirmation feedback. Do not implement competing per-app focus rings or override #atom-focus-ring. Semantic controls automatically inherit it. Respect reduced motion and the system animation preference; input must never wait for animation completion. See input-standard.md section 7.

Application-generation policy is distributed as atom/static/app-input-standard.json and injected into device workshop and Mac app-create/remix prompts. When changing the standard, update the policy asset and prompt-injection tests together. Do not maintain a divergent copy of five-way rules in provider-specific prompts; Mac packaging must include the same policy.

Cloud backup cost control: routine development/deployment must not create ECS disk snapshots, custom images, automatic snapshot policies or enable OSS versioning. Those require an explicit user request for that cloud resource. Use existing ATOM database file backup tooling; keep at most 3 completed local archives and 3 archives in its dedicated OSS prefix, and skip repeated successful backups on the same UTC day. Do not make a fresh backup per agent/tool call. Keep only 3 application release directories, preserving the active release. Never delete unrelated objects, user data, or cloud snapshots to enforce a file-backup limit. Versioned buckets require reviewed history/lifecycle retention; do not assume deleting current objects or overwriting a fixed filename reduces storage. See atom/connect/server/README.md.

Synchronized application startup: follow atom/docs/app-contract.md. Unknown identity must render connecting/loading, never a login flash. Only confirmed signed-out/401 shows login; network/permission failures show retry and preserve account-isolated data. Test delayed identity responses for signed-in, signed-out and offline. App-owned back controls must be integrated into headers/toolbars and pointer-clickable even in scene headers.

Private synchronization batches must remain bound to the account session that started them. Account/server/key changes terminate the batch and preserve its original queue; they are not record revision conflicts. Decryption failures must preserve ciphertext and last good cached content, block edits/sync until a valid retry, and never become writable placeholder text. Cover these boundaries with delayed-request and failed-decryption tests.

## Engineering philosophy and review style

User preference: apply Linus Torvalds-inspired engineering principles and direct, evidence-based code review. Do not claim to be Linus or to possess his personal experience. Critique code and decisions, not people.

- Good taste: examine data structures and ownership before adding branches. Prefer designs that make special cases ordinary; retain checks required for real boundary conditions and untrusted input.
- Never break userspace: regressions in existing applications, APIs, saved data, device pairing or established interactions are bugs even when a refactor is theoretically cleaner. Preserve compatibility; when change is necessary, provide an explicit migration and recovery path and verify existing behavior.
- Pragmatism: identify the actual failure, affected users and evidence before proposing machinery. Choose the smallest effective solution. Do not introduce speculative abstractions or rewrite working systems for theoretical elegance.
- Simplicity: keep functions focused on one responsibility and names clear. Treat more than three levels of nesting as a strong signal to rethink control flow or data representation, not a reason to hide complexity in arbitrary helpers. Reduce total complexity rather than merely line count.
- Reviews: state the concrete problem, evidence, compatibility impact and simplest repair. Separate verified defects from hypotheses. Validate the affected user flow before calling a change complete.

Creation community: keep Mac and device ordinary-user flows in the shared `atom/connect/computer/community.js` source and build the device copy with `atom/market-app/build.py`. Preserve private drafts, immutable public versions, explicit source-sharing/publication, source licenses, and same-account installation receipts. A queued delivery is never installed until the device acknowledges. Use stable request IDs on network retries. Adoption creates a separate reviewed draft and never publishes automatically. See `atom/docs/creation-community-plan.md`.

Mac presentation: ATOM Connect uses Swift/AppKit with WKWebView, not LVGL. Share creation actions and data contracts with the device, but use the Mac sidebar, desktop toolbar, responsive grids and desktop theme tokens. Do not duplicate device root navigation inside the Mac content panel. Keep scrolling inside necessary content regions. Validate desktop changes in WebKit as well as Chromium, in both appearances at normal and minimum window sizes; include project details, editing, interactive preview/return, install, publishing and advanced tools, not only root lists. Previews keep a 480×360 viewport, an accessible host-owned return control on Mac, and unload on navigation. Browser validation does not certify native file dialogs.

Product simplicity: show the current task and its next action first. Keep global navigation on root views and integrated back controls on task views. Let users describe an idea before requesting optional metadata. Preserve unsubmitted text when visiting preview or secondary actions. Group source files, version management, and other specialist tools under a clearly labeled secondary entry. Keep publication, deletion and data-access decisions explicit. Use everyday names consistently across Mac and device; explain what happened and how to recover instead of exposing internal states or claiming success early. Verify the main action fits the 480×360 viewport without page scrolling. Server operations should reuse existing read-only diagnostics with concise status and actionable next steps; do not add a second service or expose private records to simplify a dashboard.


Application release ordering: official/new/updated application delivery must publish the reviewed complete bundle and home-screen cover to the cloud marketplace first, verify the public immutable version and source digest, then distribute that version through Mac/device market clients. GitHub pushes, local seed changes, and direct SSH installs are development steps, not multi-device release completion. Preserve private drafts, user-modified forks, installation order and app data; do not silently install or overwrite. Report cloud publication, Mac visibility/download, device installation and client-runtime updates separately. Follow atom/docs/app-distribution.md and run atom/tools/verify_market_release.py before calling a release complete.

Distribution acceptance: after an application change, audit every affected delivery surface with `atom/tools/audit_app_distribution.py --require-all` against a fresh strict seed, the cloud library, Mac packaged seed, active simulator and a fresh read-only device inventory. Public official bundles must match their immutable cloud versions. Missing/offline channels are unverified, not current. Preserve valid custom icons, user forks, data and installation order. Before replacing device resources, reconcile any device-only source changes back into the repository. Exclude QA reports from runtime seed assets. GitHub upload and application publication are separate steps; record both in `atom/docs/app-distribution.md`.
